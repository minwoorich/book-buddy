# 책모임(Book Club) — 에이전트가 운영하는 사내 독서모임 설계서

작성일: 2026-09-20 · 상태: 사용자 검토 대기
관련: [[../../decisions/2026-09-20-책모임-에이전트-도입]] · [[../../plans/로드맵]]

## 1. 배경과 문제정의

지금 책벗(AI 챗봇)은 **반응형 에이전트**다. 사용자가 말을 걸면 12개 도구(검색·대출·반납·예약·희망도서·위시리스트·장소 2종 등) 중에서 골라 쓴다. "시키면 한다"까지는 완성돼 있지만, 스스로 목표를 세우거나 시간을 가로질러 움직이지는 않는다.

동시에 사이트에는 서로 만나지 못한 데이터가 쌓여 있다.

- 같은 책을 읽은 동료가 누구인지 **아무도 모른다**. `loans`에 다 있는데 화면 어디에도 드러나지 않는다.
- 리뷰는 혼자 쓰고 혼자 읽는다. 별점이 갈려도 그 차이가 대화로 이어지지 않는다.
- 장소 기능과 책 기능이 완전히 분리돼 있다. "책 읽기 좋은 장소"는 혼자 가는 곳으로만 설계돼 있다.

**책모임**은 이 셋을 하나의 목적으로 묶는다. 에이전트가 같은 책을 읽은 사람을 스스로 찾아내고, 그들이 쓴 리뷰를 읽어 토론거리를 만들고, 시간과 장소를 조율해 실제로 만나게 한다.

## 2. 목표 / 비목표

**목표**

- 에이전트가 사람의 요청 없이 모임 후보를 발견하고 제안한다 (주 1회, 쿼터 통제).
- 토론 아젠다가 일반론이 아니라 **그 참가자들이 쓴 리뷰에 근거**한다.
- 모임 일정이 시스템 안에 잡히고, 독서 달력에서 보이고, 다른 모임과 충돌하지 않는다.
- 장소 선정이 장소 페이지와 양방향으로 연결되고, 모임이 끝나면 장소 후기가 쌓인다.
- 알림 인프라를 범용으로 만들어 이후 연체·예약 알림에 재사용한다.

**비목표**

- **실제 장소 예약은 하지 않는다.** 장소는 카카오 기반 외부 카페라 시스템이 좌석을 잡을 수단이 없다. 우리가 하는 것은 "내부 일정 확정"이다. 화면 문구도 "예약"이 아니라 "장소 확정"을 쓴다.
- 외부 발송(메일·슬랙·푸시)은 하지 않는다. 앱 내 알림 + 선택적 `.ics` 내보내기까지다.
- 진행형 북클럽(아직 안 읽은 사람이 같이 읽어나가는 형태)은 범위 밖이다. **완독자 회고형**만 다룬다.
- 모임 중 채팅·실시간 기능은 없다.

## 3. 핵심: 모임의 생애주기

```
제안됨(proposed) ──관리자 승인──> 초대중(inviting) ──3명 이상 수락──> 조율중(scheduling)
                                        │ 3일 내 미달                      │ 2일 내 투표
                                        ↓                                  ↓
                                   취소(canceled) <────정원 이탈──── 확정(confirmed)
                                                                           │ 모임일 경과
                                                                           ↓
                                                                      종료(done) → 후기 요청
```

각 전이에 **기한과 실패 경로**를 둔 것이 설계의 뼈대다. 응답이 없으면 모임은 조용히 취소되고 당사자에게는 "이번엔 안 모였어요"만 간다. 영원히 떠 있는 유령 모임이 생기지 않는다.

| 전이 | 조건 | 기한 | 실패 시 |
|---|---|---|---|
| proposed → inviting | 관리자 승인 | 없음 (승인 큐에 대기) | 관리자 거절 → canceled |
| inviting → scheduling | 수락 3명 이상 | 3일 | canceled + 수락자에게 안내 |
| scheduling → confirmed | 슬롯 투표 마감 | 2일 | 최다 득표로 자동 확정. 동점이거나 무투표면 **가장 이른 슬롯** |
| confirmed → done | 모임 시각 경과 | — | — |
| confirmed → canceled | 참가 확정자가 3명 미만으로 이탈 | — | 전원 알림 |

## 4. 매칭 — 무엇을 근거로 누구를 몇 명 모으나

### 4.1 후보 발굴

기준 신호는 `loans.returned_at` 하나다. **최근 60일 내 같은 책을 완독(반납)한 사람**이 3명 이상인 책이 후보가 된다. 대출만 하고 반납하지 않은 사람은 완독으로 보지 않으므로 제외한다.

### 4.2 정원은 3~5명

2명은 모임이 아니라 잡담이고, 6명이 넘으면 전원이 발언할 수 없다. 완독자가 6명 이상이면 아래 우선순위로 5명을 고른다.

1. 리뷰를 쓴 사람 (할 말이 있다는 증거)
2. 부서 다양성을 높이는 사람
3. 최근 90일간 모임 참여가 없던 사람

### 4.3 모임 점수 — 후보가 쿼터를 넘칠 때 자르는 기준

각 항목을 0~1로 정규화해 가중합한다.

| 항목 | 가중치 | 계산 |
|---|---|---|
| 별점 분산 | 0.25 | 참가자 별점의 표준편차 / 2.0 (상한 1). **갈릴수록 높다** |
| 독서 동시성 | 0.25 | 완독 시점이 서로 가까울수록 높음 (표준편차 역수 정규화) |
| 리뷰 밀도 | 0.20 | 리뷰 쓴 사람 수 / 참가자 수 |
| 부서 다양성 | 0.15 | distinct(department) / 참가자 수 |
| 미참여 가점 | 0.15 | 최근 90일 모임 참여 0회인 사람 비율 |

**별점 분산에 가장 큰 가중치를 준 것이 이 설계의 판단이다.** 다 같이 5점을 준 모임은 덕담만 오간다. 5점과 2점이 한 방에 있어야 토론이 된다. 단 리뷰가 하나도 없으면 분산 항은 0으로 둔다(추정하지 않는다).

### 4.4 스팸 방지 쿼터

| 장치 | 값 | 막는 것 |
|---|---|---|
| 실행 주기 | 주 1회 (월요일 09:00 KST) | 무분별한 생성 |
| 1회 상한 | 최대 2개 제안 | 후보 폭주 |
| 사람 쿨다운 | 동시 1개 참여, 종료 후 4주 재초대 금지 | 특정 다독가가 매주 소집당함 |
| 책 쿨다운 | 같은 책 3개월 내 재개설 금지 | 인기 책 하나로 반복 생성 |

미니시드(책 6권·12명) 기준 "3명 이상 완독" 책은 4권이고, 60일 창 + 쿼터를 적용하면 **주당 1~2개**가 나온다. 구조적으로 폭주가 불가능하다. 임계값은 운영 DB 데이터로 한 번 더 시뮬레이션해 조정한다.

## 5. 에이전트가 실제로 하는 일

### 5.1 토론 아젠다 생성 — 이 기능의 핵심 차별점

일반적인 독서 토론 질문이 아니다. **참가자들이 쓴 리뷰 원문을 입력으로 받아** 그들 사이의 실제 의견 차를 짚는 질문을 만든다.

> "김OO님은 5점, 이OO님은 2점을 주셨습니다. 두 분 리뷰를 보면 '저자의 결론이 현장에서 통하는가'에서 갈린 것으로 보입니다. 이 지점부터 시작하시죠."

사내 데이터 없이는 만들 수 없는 산출물이다. 출력은 질문 3~5개 + 각 질문이 어느 리뷰에서 나왔는지의 근거. 근거 표시는 기존 장소 추천의 `placeEvidence` 패턴을 따른다.

리뷰가 한 건도 없는 모임은 책 메타데이터(`books.description`, 카테고리) 기반의 일반 질문으로 폴백하되, 화면에 "리뷰가 없어 일반 질문입니다"라고 밝힌다.

### 5.2 시간 후보 3개 — 충돌 회피

내부 일정 시스템이 있다는 사실의 진짜 값어치가 여기서 나온다. 참가자 전원의 일정을 이미 알고 있으므로 다음을 걸러낸다.

- 참가자 누군가의 **다른 confirmed 모임과 겹치는 시간 제외**
- 아직 그 책을 대출 중인 참가자가 있으면 **그의 `due_at` 이전**으로 (반납하고 나면 책 없이 토론하게 된다)
- 사내 현실에 맞는 슬롯만: 점심 12:00–13:00 / 퇴근 후 18:30–20:00, 다음 주 평일
- 참가자 사업장이 2개 이상이면(본사·엠시스·이엠엑스 좌표는 `shared/constants/company.ts`에 있음) 이동시간을 고려해 저녁 슬롯에 가중

남은 슬롯 중 상위 3개를 후보로 올린다. 3개가 안 나오면 나오는 만큼만.

### 5.3 장소 후보 3곳 — 개인 독서와 다른 점수식

**현재 장소 태그 6종은 전부 "혼자 읽기" 기준이다**(`quiet` 조용해요, `outlet` 콘센트 있어요 등). 북클럽은 떠들어야 하는 자리라 `quiet`가 높은 곳은 오히려 나쁜 후보다. 모임 전용 점수식을 분리한다.

| 항목 | 가중치 | 비고 |
|---|---|---|
| 중간 지점 근접도 | 0.30 | 참가자 사업장 좌표의 평균 지점 기준 거리 |
| `spacious` 비율 | 0.25 | 4인 이상이면 0.30으로 상향 |
| `long-stay` 비율 | 0.20 | |
| 후기 수 | 0.15 | log 스케일 (검증된 장소 우대) |
| `noisy` 역가중 | 0.10 | 과반이 noisy면 감점 |

`quiet`는 **가점도 감점도 아닌 중립**으로 둔다. 개인 추천에서는 최상위 신호인 태그가 여기서는 무의미해진다는 점이 이 분리의 이유다.

### 5.4 사후 — 데이터 플라이휠

모임 다음 날 참가자 전원에게 **그 장소의 후기 요청** 알림이 간다.

```
모임 확정 → 모임 진행 → 장소 후기 3~5건 유입 → 장소 추천 정확도 ↑ → 다음 모임 장소 선정 ↑
```

지금 `place_reviews`는 개인이 자발적으로 쓸 때만 늘어난다. 모임이 그 수도꼭지를 연다.

## 6. 데이터 모델

```sql
CREATE TABLE IF NOT EXISTS clubs (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  book_id INTEGER NOT NULL REFERENCES books(id),
  status TEXT NOT NULL DEFAULT 'proposed'
    CHECK (status IN ('proposed','inviting','scheduling','confirmed','done','canceled')),
  -- 에이전트 산출물
  agenda TEXT NOT NULL DEFAULT '[]',          -- [{question, evidence:[{userId,quote}]}]
  match_score REAL NOT NULL DEFAULT 0,
  match_reason TEXT NOT NULL DEFAULT '',      -- 왜 이 조합인지 (관리자 승인 화면용)
  -- 일정
  candidate_slots TEXT NOT NULL DEFAULT '[]', -- ["2026-09-25T19:00", ...] 최대 3, **항상 시간순 정렬**
  meet_at TEXT,                               -- 확정 시각
  invite_expires_at TEXT,
  vote_expires_at TEXT,
  -- 장소 (내부 일정용 확정일 뿐, 실제 예약 아님)
  place_kakao_id TEXT, place_name TEXT, place_lat REAL, place_lng REAL,
  place_decided_at TEXT,
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  canceled_reason TEXT);

CREATE TABLE IF NOT EXISTS club_members (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  club_id INTEGER NOT NULL REFERENCES clubs(id),
  user_id INTEGER NOT NULL REFERENCES users(id),
  role TEXT NOT NULL DEFAULT 'member' CHECK (role IN ('host','member')),
  invite_status TEXT NOT NULL DEFAULT 'invited'
    CHECK (invite_status IN ('invited','accepted','declined')),
  responded_at TEXT,
  UNIQUE(club_id, user_id));

CREATE TABLE IF NOT EXISTS club_votes (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  club_id INTEGER NOT NULL REFERENCES clubs(id),
  user_id INTEGER NOT NULL REFERENCES users(id),
  slot_idx INTEGER NOT NULL,
  UNIQUE(club_id, user_id, slot_idx));

-- 범용 알림. 책모임 전용으로 만들지 않는다 — 연체·예약 알림에 그대로 재사용한다.
CREATE TABLE IF NOT EXISTS notifications (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id INTEGER NOT NULL REFERENCES users(id),
  type TEXT NOT NULL,
  title TEXT NOT NULL, body TEXT NOT NULL DEFAULT '',
  link TEXT,
  read_at TEXT,
  created_at TEXT NOT NULL DEFAULT (datetime('now')));
CREATE INDEX IF NOT EXISTS idx_notifications_user ON notifications(user_id, read_at);
```

**별도 일정 테이블을 만들지 않는 이유**: 모임 하나당 일정이 하나뿐이라 `clubs.meet_at`으로 충분하고, 충돌 검사도 `club_members ⋈ clubs WHERE status='confirmed'` 한 번이면 끝난다. 모임당 여러 회차가 필요해지면 그때 분리한다.

호스트는 에이전트가 정한다 — 리뷰를 쓴 사람 중 모임 참여 이력이 가장 많은 사람, 없으면 최초 완독자. **호스트가 초대를 거절하면** 수락자 중 같은 기준으로 재지정한다(수락자가 없으면 모임은 어차피 정원 미달로 취소된다).

## 7. 알림

발송 시점 6개 (`type` 값):

| type | 언제 | 받는 사람 |
|---|---|---|
| `club_invited` | 관리자 승인 직후 | 초대된 전원 |
| `club_invite_expiring` | 응답 마감 하루 전 | 미응답자 |
| `club_vote_request` | scheduling 진입 | 수락자 |
| `club_confirmed` | **시간** 확정 (scheduling → confirmed) | 참가자 |
| `club_place_set` | **장소** 확정 또는 변경 | 참가자 |
| `club_reminder` | 모임 전날 | 참가자 |
| `club_review_request` | 모임 다음 날 | 참가자 |

시간 확정과 장소 확정은 **별개의 사건**이다. 시간은 투표 마감으로 자동 확정되고 장소는 호스트가 고른다. 순서가 정해져 있지 않으므로 알림도 둘로 나눈다. 장소가 이미 정해진 상태에서 시간이 확정되면 `club_confirmed` 본문에 장소를 함께 담아 알림 두 개가 연달아 가지 않게 한다.

헤더에 벨 아이콘 + 미확인 배지. 외부 발송 인프라가 없으므로 앱 내 폴링이다(60초 간격, 페이지 포커스 시 즉시 1회). 이미 일정이 있는 사람이 새 초대를 받으면 초대 카드에 **"9/25 19:00에 이미 일정 있음"**이 함께 표시된다.

## 8. 화면

### 8.1 `/clubs` — 책모임

상단 메뉴 라벨은 "모임". 현재 nav가 7개라 8번째는 빽빽하므로, "리뷰"를 내 서재 하위로 넣는 정리를 함께 검토한다.

```
┌ 나의 초대 (2)           ← 여러 모임에 동시 초대 가능
│  [하드씽 · 4명 · 응답 D-2 · ⚠ 9/25 19:00 일정 있음]  [함께 자라기 · 3명 · D-1]
├ 내 응답 필요
│  [팀장의 탄생 · 시간 투표 D-1]
├ 참여 중
│  [클린 코드 · 9/25(목) 19:00 · 스타벅스 광교점]   ← 미니 지도 + 아젠다 미리보기
└ 지난 모임
```

### 8.2 `/clubs/[id]` — 모임 상세

책 정보 · 참가자(부서 표시) · **아젠다 전문과 근거 리뷰 인용** · 시간 투표 · 장소 후보/확정 · `.ics` 내보내기.

### 8.3 관리자 승인 큐

`/admin` 안의 섹션. 제안마다 책·참가자·매칭 점수·**왜 이 조합인지(`match_reason`)**·아젠다 초안을 보여주고 승인/거절한다. 테스트와 운영을 위해 "매처 지금 실행" 버튼을 둔다.

### 8.4 독서 달력 — `ReadingCalendar` 일반화

현재 `loans` 배열만 받아 완독만 찍는 구조를 `events` 배열로 바꾼다. 한 칸에 세 종류가 공존한다.

| 이벤트 | 시점 | 표현 |
|---|---|---|
| 완독 | 과거 | 지금처럼 책 표지 |
| 반납 예정 | 미래 | 날짜 모서리 얇은 띠 (지금 없는 기능 — 덤으로 생김) |
| 모임 | 미래 | 📖 칩 + 시각 + 장소 이름 |

여기에 "시스템이 자리를 잡아둔다"의 UI를 얹는다 — **확정 전 후보 시간 3개를 점선으로 미리 표시**. 확정되면 점선이 실선이 되고 나머지 둘은 사라진다.

`ReadingCalendar`는 현재 `props.loans`에 강결합돼 있고 `dayLoans`/`coverIndex`가 전부 loan 전제다. 이 일반화는 이 설계에 필요한 **범위 내 리팩터링**이다.

## 9. 장소 페이지 연동

양방향으로 뚫는다.

**장소 → 모임**

- 장소 카드·요약카드에 **"이 곳을 ○○ 모임 장소로"** 버튼. 단 **내가 호스트이고 아직 모임 전날이 지나지 않은** 모임이 있을 때만 노출한다(없으면 UI가 지저분해진다). 장소는 `scheduling` 진입 시점부터 **모임 전날까지** 정하거나 바꿀 수 있고, 바꿀 때마다 `club_place_set` 알림이 나간다. 전날 이후에는 잠근다 — 당일에 장소가 바뀌면 사람이 헛걸음한다.
- 확정된 장소에는 **모임 배지** — "9/25 『하드씽』 모임 예정". 사내 후기 옆에 "여기서 우리 회사 사람들이 모인다"는 흔적이 남는다.

**모임 → 장소**

- 모임 상세의 "장소 고르기"가 `/places?forClub=12`로 이동한다. 이 컨텍스트에서 장소 페이지가 **모임 모드**로 바뀐다.
  - 지도 기준점이 내 사업장이 아니라 **참가자 사업장들의 중간 지점**으로 이동하고, 그 지점에 특수 핀을 찍는다.
  - 정렬이 §5.3의 모임 점수식으로 교체된다.
  - 상단에 "『하드씽』 모임 장소 고르는 중 · 4명" 띠.

## 11. 주기 실행

Nuxt 4.5(Nitro 2)의 `server/tasks/` + `scheduledTasks`를 쓴다. Railway가 단일 장수 컨테이너라 인프로세스 스케줄러가 동작한다. 실험적 플래그가 문제되면 Nitro 플러그인 + `setInterval` 폴백으로 바꾼다. 어느 쪽이든 마지막 실행 시각을 DB에 남겨 **재시작 직후 중복 실행을 막는다**.

주기 작업 3종:

1. **매처** (주 1회 월 09:00) — 후보 발굴 → 제안 생성
2. **기한 처리** (매일 09:00) — 초대 만료, 투표 마감 자동 확정, 모임일 경과 → done
3. **알림** (매일 09:00) — 마감 임박, 전날 리마인드, 사후 후기 요청

## 12. 엣지 케이스

- **확정 후 이탈로 3명 미만** → 모임 취소, 전원 알림. 시간을 다시 잡지는 않는다(복잡도 대비 실익이 없다).
- **책이 삭제됨** → 진행 중 모임은 유지하되 화면에 "삭제된 도서"로 표기한다.
- **게스트 계정** → 초대 대상에서 제외한다. 시연용 계정이 모임에 묶이면 해제 시 모임이 깨진다.
- **매처가 LLM 호출에 실패** → 그 회차는 제안 0건으로 넘기고 `ai_usage`에 실패를 남긴다. 부분 결과를 저장하지 않는다.
- **슬롯 후보가 0개** (전원 일정이 꽉 참) → 제안을 canceled로 두고 관리자에게만 알린다.
- **참가자 전원이 같은 부서** → 부서 다양성 점수만 0이 되고 모임은 성립한다(강제 배제하지 않는다).

## 13. 테스트 전략

기존 `tests/` 패턴(vitest, 순수 함수 위주)을 따른다. TDD 대상은 특히 다음이다.

- **매칭 점수식** — 별점 분산이 클수록 점수가 높은가, 리뷰가 없으면 분산 항이 0인가
- **쿼터** — 사람 쿨다운·책 쿨다운·회차 상한이 실제로 후보를 자르는가
- **멤버 선정** — 완독자 6명 이상에서 부서 다양성이 실제로 올라가는가
- **슬롯 생성** — 충돌하는 시간이 제외되는가, 대출 중 참가자의 `due_at` 이후가 배제되는가
- **상태 전이** — 각 기한에서 올바른 상태로 가는가, 정원 미달이 canceled가 되는가
- **투표 마감** — 동점일 때 이른 시각이 뽑히는가
- **장소 점수식** — `quiet`가 순위에 영향을 주지 않는가 (개인 추천과의 분리 검증)

## 14. 단계 분할

최종적으로 전 범위를 구현한다. 아래는 구현 순서일 뿐 범위 축소가 아니다.

### 1단계 — 모임의 뼈대와 알림

스키마 4종 · 매처(점수식·쿼터) · 아젠다 생성 · 관리자 승인 큐 · `/clubs` 목록·상세 · **범용 알림 인프라 + 헤더 벨** · 주기 작업(매처/기한).
알림이 1단계에 있어야 초대가 도착할 수 있으므로 함께 간다. 이 단계 끝에 "제안 → 승인 → 초대 → 수락"이 동작한다.

### 2단계 — 일정

충돌 회피 슬롯 생성 · 투표와 마감 자동 확정 · **`ReadingCalendar` 일반화**(완독/반납예정/모임/후보 점선) · `.ics` 내보내기 · 전날 리마인드.
이 단계 끝에 "언제 만나는가"가 시스템 안에 잡힌다.

### 3단계 — 장소와 플라이휠

모임 전용 장소 점수식 · `/places?forClub=` 모임 모드(중간 지점·정렬 교체) · 장소 카드의 "모임 장소로" 버튼 · 확정 장소 모임 배지 · 사후 후기 요청 알림.
이 단계 끝에 "어디서 만나는가"와 후기 순환이 닫힌다.
