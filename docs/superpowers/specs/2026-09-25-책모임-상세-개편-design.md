# 책모임 상세 개편 — 후보 시간 제안·즉시 확정·채팅 · 설계서

작성 2026-09-25 · 상태: **구현 완료(2026-09-25, feat/club-detail)** · 전제 [[2026-09-24-책모임-직접개설-design|직접 개설 설계서]](구현·배포 완료) · [[2026-09-20-책모임-design|책모임 설계서]]

## 1. 왜

직접 개설을 써 본 민우의 지적 세 가지.

1. **"사전 마감이 없다"** — "모집 마감 → 시간 잡기"가 그것이었지만 3명 미만이면 비활성이고 화면이 이유를 말하지 않아 없는 기능처럼 보였다. 규칙 자체도 개설자에게 너무 빡빡하다.
2. **"시간 잡기·투표가 없다"** — 시간은 마감 *뒤에* 시스템이 후보를 만들어야 보였다. 모집 중에는 "언제 만나는지"를 아무도 모른 채 참여를 결정해야 했다.
3. **"채팅이 없다"** — 글·댓글 게시판은 모임 전 잡담 용도에 무겁다.

## 2. 결정 (2026-09-25 브레인스토밍)

| 질문 | 결정 |
|---|---|
| 모집 중 시간 | **개설자가 후보 시간을 미리 제안하고 참가자가 모집 중에 투표.** 후보를 안 내면 지금처럼 마감 후 시스템 후보 |
| 사전 마감 최소 인원 | **개설자 마음대로(1명이어도).** 대신 확정 뒤에도 참여할 수 있게 |
| 채팅 | **게시판을 실시간 채팅으로 교체**(SSE 수신 + POST 발신). 참가자만, 모임당 방 하나 |
| 상세 페이지 | 전면 재배치 — 액션 줄 하나, 데스크톱 2단(일정·참가자·토론 / 채팅) |

## 3. 시간 — 후보 제안 · 모집 중 투표 · 개설자 확정

### 3.1 후보 시간

- 개설 폼과 상세(모집 중, 개설자)에서 **후보 시간 0~5개**. 각 후보는 KST 날짜 + 시각(30분 단위, 기본 18:30). 지금 시각 이후만, 서로 다른 값만. 저장은 기존 `clubs.candidate_slots`(ISO, 시간순 정렬 — 기존 불변량 유지).
- 후보를 **고치면** 표는 인덱스가 아니라 ISO로 다시 맞춘다: 남은 후보의 표는 유지, 사라진 후보의 표는 삭제(`club_votes`는 `slot_idx`라 재계산해서 다시 쓴다). 참가자에게 알림 없음(채팅에 시스템 메시지로 남긴다 — §5.4).
- 길이: 기존 `slotDurationMinutes`(KST 12시 → 60분, 그 외 90분) 그대로.

### 3.2 모집 중 투표

- 사람 모임은 `inviting`에서도 `vote()` 허용(수락자만, 다중 선택). `vote_expires_at`은 사람 모임에서 쓰지 않는다(null).
- 에이전트 모임과 달리 **전원 투표로 자동 확정하지 않는다** — 확정은 개설자의 몫(§3.3)이거나 기간 만료(§3.4).

### 3.3 시간 확정(= 사전 마감)

`POST /api/clubs/:id/confirm { slot?: string }` — 개설자만, `inviting`만, **인원 제한 없음**.

- `slot`이 없으면 **최다 득표**(동점·무표면 가장 이른 것; 이미 지난 후보는 제외). 있으면 그 ISO가 후보 중 하나여야 한다. 확정 가능한 미래 후보가 하나도 없으면 400 "지난 시간이에요. 후보를 고쳐주세요".
- 결과: 미응답 초대 → `declined`, 아젠다 생성(기존 `generateAgenda`), `inviting → confirmed`(조율 단계 건너뜀), `meet_at` 설정, 수락자에게 `club_confirmed`(기존 문구·`placeSuffix`).
- 후보가 **하나도 없으면** 기존 `closeRecruiting` 경로(시스템 후보 3개 → `scheduling` → 투표 → 확정). 즉 `close-recruiting`은 남고, 화면은 후보 유무에 따라 "시간 확정" 또는 "모집 마감 → 시간 잡기"를 보인다.
- 화면 확인창: 후보별 득표 막대와 라디오(기본 = 최다 득표), "이 시간으로 확정".

### 3.4 기간 만료(`club:deadlines`)

`expireRecruiting`의 사람 모임 분기:
- 후보 있음: 수락 **2명 이상**이면 §3.3과 같은 규칙으로 자동 확정. 개설자뿐이면 취소 "모집 기간에 아무도 오지 않았어요".
- 후보 없음: 지금 규칙(3명↑ 조율 / 미만 취소).

### 3.5 확정 뒤 참여

- 사람 모임이 `confirmed`이고 **모임 전날 23:59 KST 이전**이며 수락 + 초대 대기 < 정원이면 `join`이 열린다(공개 참여·초대 모두). 들어오면 `accepted`, 개설자에게 `club_joined`, 새 참가자에게는 확정 시각·장소가 담긴 `club_confirmed`를 바로 보낸다(리마인드·후기 요청은 기존 로직이 수락자 기준이라 자동 포함).
- `leave`도 같은 창 안에서 허용(개설자 제외). 확정 후 이탈로 수락자가 0이 되지는 않는다(개설자는 못 나감).
- `canViewClub`: 사람 모임은 `inviting`뿐 아니라 **`confirmed`도 누구나**(자리 있는 모임을 보고 들어올 수 있게).
- 목록 "모집 중" 구획 → **"열려 있는 모임"**: `inviting` + (`confirmed` · 전날 전 · 정원 미만). 카드 라벨 "확정 · 자리 있어요".
- 확정 후 참여자는 이미 정해진 시간에 동의한 것으로 본다(투표 없음).

### 3.6 에이전트 모임

후보 생성·`scheduling`·전원 투표 확정·마감·리마인드 전부 불변. `confirm` API는 사람 모임 전용(에이전트 모임 400).

## 4. 스키마

`clubs`·`club_votes` 변경 없음(후보는 `candidate_slots`, 표는 `club_votes`). 새 테이블:

```sql
CREATE TABLE IF NOT EXISTS club_messages (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  club_id INTEGER NOT NULL REFERENCES clubs(id),
  user_id INTEGER REFERENCES users(id),          -- NULL이면 시스템 메시지
  kind TEXT NOT NULL DEFAULT 'chat' CHECK (kind IN ('chat','system')),
  body TEXT NOT NULL,
  created_at TEXT NOT NULL DEFAULT (datetime('now')));
CREATE INDEX IF NOT EXISTS idx_club_messages_club ON club_messages(club_id, id);
CREATE TABLE IF NOT EXISTS club_message_reads (
  club_id INTEGER NOT NULL REFERENCES clubs(id),
  user_id INTEGER NOT NULL REFERENCES users(id),
  last_read_id INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (club_id, user_id));
```

`club_posts`는 코드에서 제거하고 테이블은 그대로 둔다(운영 0건; 다음 정리 때 DROP).

타입: `ClubMessage { id, clubId, userId: number | null, userName: string | null, department: string | null, kind: 'chat' | 'system', body, createdAt }`. `Club`에 `unreadMessages: number`(목록·상세용, 요청자 기준)와 `myVote`는 두지 않는다 — `votes`가 이미 있다.

## 5. 채팅

### 5.1 API

| 경로 | 누구 | 뭐 |
|---|---|---|
| `GET /api/clubs/:id/messages?before=<id>&limit=50` | 수락자 | 최근 메시지(오래된 → 최신 순으로 돌려줌), `before`로 위로 더 |
| `POST /api/clubs/:id/messages { body }` | 수락자, `done`/`canceled` 아님 | 1~500자 trim. 저장 → 팬아웃 → 저장된 메시지 반환 |
| `POST /api/clubs/:id/messages/read { lastReadId }` | 수락자 | 읽음 표시(뒤로는 안 감) |
| `GET /api/clubs/:id/stream?userId=&guestToken=` | 수락자 | SSE. `EventSource`는 헤더를 못 붙이므로 쿼리로 인증(`guestRepo.resolveUser`). 이벤트 `message`(JSON `ClubMessage`), 25초마다 `ping` |

### 5.2 팬아웃

`server/utils/clubStream.ts`: `subscribe(clubId, send): unsubscribe`, `publish(clubId, message)`. 프로세스 내 `Map<number, Set<fn>>`. Railway 단일 컨테이너 전제 — 인스턴스가 늘면 Redis 같은 브로커가 필요하다(운영 노트).

### 5.3 안 읽은 수와 알림

- `unreadMessages` = `club_messages.id > last_read_id AND kind='chat' AND user_id != me` 수. `GET /api/clubs`(목록)와 `GET /api/clubs/:id`에 실린다. 카드에 "새 메시지 n".
- 알림 `club_chat`: 게시판 규칙 승계 — **모임당 KST 하루 1건**, 링크 `/clubs/:id?chat=YYYY-MM-DD`, 작성자와 **그 순간 스트림에 붙어 있는 사람**은 제외. 메시지마다 알림은 없다.

### 5.4 시스템 메시지

개설자가 후보를 고치거나 시간을 확정하거나 누가 들어오고 나갈 때 `kind='system'`으로 한 줄("김민우 님이 후보 시간을 고쳤어요 · 9/29(화) 18:30, 10/1(목) 18:30" / "이서연 님이 참여했어요" / "시간이 정해졌어요 · 9/29(화) 18:30"). 알림 대상이 아니고 안 읽은 수에도 세지 않는다.

### 5.5 게시판 제거

`clubPostRepo`·`clubPostService`·`posts` API 3개·`PostBoard.vue`·`club_post` 알림·관련 테스트 삭제. `ClubPost` 타입 삭제. `[id].vue`의 `?posts=` 스크롤은 `?chat=`으로.

```
│ 칩 · 완독 배지               │ │ [메시지 입력   ][보내기]│

│ …                          │

```

- **헤더**: eyebrow `BOOK CLUB` + 상태 배지(`모집 중 D-4` / `확정 · 9/29(화) 18:30` / `시간 조율 중` / `끝난 모임` / `취소`). 에이전트 모임은 소개 대신 `matchReason`.
- **액션 줄**(`.btn` 나열, 첫 번째만 `.primary`):
  - 개설자·모집 중: `시간 확정`(후보 있을 때) 또는 `모집 마감 → 시간 잡기`(후보 없을 때) · `초대하기` · `모임 접기`
  - 비멤버·열린 모임: `참여하기`(정원 차면 "정원이 찼어요" 문구)
  - 참가자(개설자 아님)·열린 모임: `참여 취소`
  - 초대받은 사람: `참여할게요` · `이번엔 어려워요`(기존 respond)
  - 확정·개설자·전날 전: `장소 고르기/바꾸기`(기존) · 확정 모임 전원: `내 캘린더에 추가`
- **일정 패널**(`.panel`): 후보 시간 목록 + 득표 막대(`--bar-track/--bar-fill`, 최다 득표는 레드) + 체크박스(수락자) + "투표 저장". 개설자 "후보 고치기"는 인라인 편집(날짜·시각 줄 추가/삭제, 최대 5). 확정되면 시각·장소·카카오맵·ics. 에이전트 모임의 `scheduling`은 기존 투표 UI를 이 패널 안에 같은 모양으로.
- **참가자**: 칩(`.chip` 꼴, 진행·완독·불참).
- **토론 질문**: 기존, `confirmed` 이후에만. 모집 중엔 "시간이 정해지면 참가자 리뷰로 토론 질문을 만들어 드려요".
- **채팅 패널**(`ClubChat.vue`): 데스크톱 오른쪽 sticky(`top: 24px`, 높이 `calc(100vh - 120px)`), 모바일은 맨 아래 고정 높이 420px. 말풍선(내 것은 오른쪽·`--red-tint`), 이름·부서·시각(KST), 시스템 메시지는 가운데 흐리게, 날짜 구분선, 위로 스크롤하면 이전 50개, Enter 전송(Shift+Enter 줄바꿈), 연결 끊김 표시. 열리면 읽음 처리.
- 전부 사이트 관례·토큰. 모바일 390px 넘침 없음.

### 6.1 목록·카드

"모집 중 (n)" → **"열려 있는 모임"**; 카드에 후보 시간 첫 두 개("9/29(화)·10/1(목) 저녁") 또는 확정 시각, "새 메시지 n" 배지.

### 6.2 개설 폼

`/clubs/new`에 **후보 시간** 그룹(선택): 줄마다 날짜 `<input type=date>` + 시각 셀렉트(30분 단위, 기본 18:30), "+ 시간 추가"(최대 5), 지난 시각·중복은 400 문구. `POST /api/clubs`에 `candidateSlots?: string[]`.

## 7. API 정리

신규: `POST /api/clubs/:id/confirm`, `PUT /api/clubs/:id/candidates { slots: string[] }`(개설자·모집 중·0~5개), `GET|POST /api/clubs/:id/messages`, `POST /api/clubs/:id/messages/read`, `GET /api/clubs/:id/stream`.
변경: `POST /api/clubs`(candidateSlots), `POST /api/clubs/:id/votes`(사람 모임 `inviting` 허용), `POST|DELETE /api/clubs/:id/join`(확정 후 창), `GET /api/clubs/recruiting` → 열린 모임, `GET /api/clubs`·`/:id`(unreadMessages).
삭제: `posts` 3개.

## 8. 코드 배치

- `clubRecruitService`: `setCandidates`, `confirm`, `join/leave`의 확정 후 창, `expireRecruiting` 분기 수정, `create`에 candidateSlots.

- `server/repositories/clubMessageRepo.ts`, `server/services/clubChatService.ts`, `server/utils/clubStream.ts`.
- `clubRepo`: `setCandidateSlotsOnly(id, slots)`(vote_expires_at 안 건드림), `replaceVotes(clubId, rows)`, `listOpen(nowIso)`, `unreadCounts(userId, clubIds)`.

## 9. 테스트

- `clubCandidates`: 정규화(과거·중복·6개·30분 단위 아님) · 표 재매핑 · 득표 선택(동점→이른 것, 지난 것 제외).
- `clubRecruitService`: 후보 설정/수정 후 표 유지·삭제 · 모집 중 투표 허용(에이전트 `inviting`은 여전히 400) · 확정(기본/지정/1명/지난 후보만이면 400/후보 없으면 400 안내) · 만료(후보 있음 2명↑ 확정·1명 취소 / 후보 없음 기존) · 확정 후 참여·취소(창·정원·전날 잠금·새 참가자 알림) · 확정 후 `canViewClub`.
- `clubChatService`: 권한(초대만·비멤버 403), 길이, 끝난 모임 400, 읽음 단조 증가, unread 계산(시스템·내 메시지 제외), 하루 1건 알림(접속자 제외), 시스템 메시지 발행.
- `clubStream`: 구독/발행/해제 유닛.
- 기존 게시판 테스트 삭제. 화면은 헤드리스(개설에 후보 2개 → 참여자 투표 → 개설자 확정 → 확정 후 참여 → 채팅 왕복(두 탭) → 모바일).

## 10. 하지 않는 것

- 메시지 수정·삭제·이미지·멘션·읽음 표시(누가 읽었는지).
- 다중 인스턴스 팬아웃(브로커).
- 에이전트 모임의 흐름 변경.
- 후보 시간을 사람 모임에서 시스템이 추천하는 기능(후보 없음 = 기존 경로).

## 11. 운영 노트

- SSE 연결은 프로세스 메모리에 산다 — 재배포 시 끊기고 `EventSource`가 재접속한다. 컨테이너 1개 전제.
- `club_posts` 테이블은 남는다. 다음 마이그레이션 정리 때 DROP.

## 12. 구현 노트 (2026-09-25)

- 참여 창 판정은 `shared/utils/clubOpen.ts`(`joinWindowOpen`·`hasSeat`·`reservedCount`)로 서버·화면이 공유. "전날까지" 경계는 기존 `placeLocked`와 같다.
- **초대 수락도 참여 창을 따른다** — `clubService.respond`가 사람 모임이면 확정 뒤에도(전날까지) 수락을 받고, 확정 모임에 들어온 사람에겐 `club_confirmed`를 바로 보낸다(`notifyConfirmedTo` 공유). §3.5는 `join`만 적고 초대 경로를 빠뜨렸다(리뷰가 잡음).
- 확정 알림 문구는 `clubService.confirmWith`에 한 번만 있고 개설자 확정·전원 투표 확정이 같이 쓴다.
- `GET /api/clubs/recruiting` → **`/api/clubs/open`**. `Club.unreadMessages`는 선택 필드로, 목록·상세·open 핸들러가 채운다.
- SSE 핸들러는 접속 직후 `ping` 하나를 먼저 밀어 헤더를 내보낸다 — Node는 첫 write까지 헤더를 버퍼링해서 `EventSource`가 25초간 "connecting"에 머문다.
- 채팅 패널은 상세 페이지가 `:key="club.id"`로 모임마다 리마운트한다. 컴포넌트 이름은 Nuxt 접두사 병합 규칙에 따라 `<ClubChat>`(`components/club/ClubChat.vue`).
- 시스템 메시지 문구: "○○ 님이 참여했어요 / 나갔어요", "후보 시간을 고쳤어요 · 9/29(화) 18:30 · …", "시간이 정해졌어요 · …". 채팅 시각은 KST 고정.
