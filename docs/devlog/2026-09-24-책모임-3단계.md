## 무엇이 생겼나

모임의 "어디서 만나는가"가 잡히고, 모임이 끝나면 장소 후기가 쌓이는 순환이 닫힌다.

- **사업장 매핑·중간 지점** (`shared/constants/company.ts`) — 운영 `users.company`는 `바텍 / 바텍이우홀딩스 / 바텍엠시스 / 레이언스 / 바텍네트웍스`라 `VATECH_OFFICES` 키와 직접 대응하지 않는다. 이름에 '엠시스'면 수원, '이엠엑스'면 용인, 그 외는 동탄 본사. 중간 지점 = 수락자 사업장 좌표의 평균(빈 배열이면 본사).
- **모임 전용 장소 점수식** (`server/utils/clubPlace.ts`, 순수 함수) — 중간 지점 근접 0.30 · `spacious` 0.25(4명 이상 0.30) · `long-stay` 0.20 · 후기 수 0.15(`log1p(n)/log1p(10)`) · `noisy` 역가중 0.10(과반이면 0, 후기 없으면 1). **`quiet`는 중립** — 개인 추천의 최상위 신호가 여기서는 무의미하다는 게 점수식을 분리한 이유. 근거 문구는 "중간 지점에서 105m · 자리 넓어요 1 · 후기 3개"처럼 사람이 읽는 형태.
- **장소 확정** (`clubService.setPlace`) — 호스트만(403) → `scheduling`·`confirmed`에서만(400) → 모임이 지났거나 **당일(KST)이면 잠금**(400) → 검증. 확정하면 수락자 전원에게 `club_place_set`("시간은 투표로 정해져요 · 우지커피…"). `meet_at`은 절대 건드리지 않는다(2단계 이월: `slotDurationMinutes`가 KST 시로 길이를 추정하므로).
- **후보 조립** (`placeCandidates`) — 카카오 로컬 `카페`·`북카페`·`도서관` × 반경 5km × 키워드당 5건 → kakaoId 중복 제거 → 사내 후기 집계 → 점수 정렬 → **상위 8곳**. 후기 없는 곳도 근접도만으로 든다(배제하면 플라이휠이 시작되지 않는다). 카카오 검색은 `search` 함수 주입으로 테스트.
- **사후 후기 요청** (`requestPlaceReviews`) — `done` + 장소 있음 + `done_at`의 다음 날(KST)이 오늘이면, 아직 그 장소에 후기를 쓰지 않은 수락자에게 `club_review_request` 한 번. 링크 `/places?review=<kakaoId>&name=&lat=&lng=` — 카카오에 id 단건 조회가 없어 이름·좌표를 실어 보내고 장소 페이지가 후기 시트를 바로 연다. `club:deadlines`가 이 일도 맡는다.
- **API** — `PUT /api/clubs/:id/place`, `GET /api/clubs/:id/place-candidates`(멤버만, 키 없으면 503), `GET /api/clubs/upcoming-places`(확정 모임의 장소 — 정적 라우트가 `[id]`보다 우선함을 curl로 확인).
- **상세 화면** — "언제 / 어디서" 블록. 장소 없으면 "장소 고르기" → `/places?forClub=<id>`, 있으면 "(장소 확정) 카카오맵 · 장소 바꾸기", 잠기면 안내 문구, ics 버튼은 맨 뒤.
- **장소 페이지 모임 모드** — 기존 `?picks=1` 추천 모드와 같은 방식으로 `?forClub=<id>`. 띠("『함께 자라기』 모임 장소 고르는 중 · 참가자 3명의 중간 지점 기준"), 지도 중심을 중간 지점으로, 정렬을 모임 점수식으로 교체, 카드마다 근거 문구와 호스트 전용 "모임 장소로" 버튼(쿼터상 호스트가 고를 수 있는 모임은 항상 최대 1개라 분기 없음). 일반 목록에서도 확정 장소 카드에 **"📖 9/29(화) 『함께 자라기』 모임 예정"** 배지 — 누구에게나 보인다.
- **인가 테스트 방식** — 2단계 최종 리뷰가 "호스트 전용 장소 확정은 인가 버그가 데이터 버그가 되는 첫 엔드포인트"라고 했다. h3 하네스를 만드는 대신 **인가를 서비스 층에 두고** 서비스 테스트로 403/400 순서와 잠금 경계(월 19:00 KST 허용 / 화 01:00 KST 잠금)를 검증했다.

## 시각 확인

헤드리스 Chrome/CDP로 로컬 DB의 모임을 실제로 진행: 후보 8곳(중간 지점 = 본사, 1위 우지커피 "중간 지점에서 105m · 자리 넓어요 1 · 오래 있기 좋아요 1 · 시끄러워요 1 · 후기 3개") → 비호스트 PUT 403 → 상세 "장소 고르기" → `/places?forClub=1` 띠·근거·버튼 8개 → 클릭 → 상세 "우지커피 (장소 확정) 카카오맵 · 장소 바꾸기" → 다른 참가자 벨에 `club_place_set` → confirmed로 올린 뒤 `/places` 카드 배지 "9/29(화) 『함께 자라기』 모임 예정" → `?review=` 링크로 후기 시트 즉시 열림 → 모바일 390px 상세 넘침 없음.

## 운영 노트

- `club:deadlines`(00:00Z = 09:00 KST)가 이제 **후기 요청**까지 맡는다. 창은 종료 +1일부터 +7일(KST 날짜)이라 cron을 며칠 놓쳐도 다음 실행이나 관리자 "기한 작업 지금 실행"이 따라잡는다(메시지에 "후기 요청 N명"). 7일이 지나면 안 나간다 — 의도된 상한(최초 배포 시 과거 모임 백필 방지).
- 후보 검색은 서버가 `NUXT_KAKAO_REST_KEY`(runtimeConfig `kakaoRestKey`)로 카카오 로컬을 호출한다 — 키는 클라이언트에 노출되지 않는다. 키가 없으면 503, 화면은 서버 오류 문구를 alert로 보이고 모임 모드를 풀어 일반 장소 목록으로 떨어진다.
- 마이그레이션 없음 — 장소 컬럼(`place_kakao_id`·`place_name`·`place_lat`·`place_lng`·`place_decided_at`)은 1단계 스키마에 이미 있었다.
- 장소 잠금은 **모임 당일 00:00 KST**부터다. 전날 09:00 KST 리마인드가 나간 뒤 그날 안에 장소가 바뀔 수 있는데, `club_place_set`이 그 변경을 알리므로 리마인드를 다시 보내지 않는다.

## 이월

- `setPlace` 같은 장소 재제출 no-op(더블탭 중복 알림).
- `placeCandidates`의 `Promise.all` → `allSettled`로 부분 결과 유지.
- 후기 요청 dedup을 장소 링크가 아니라 모임 기준으로(같은 장소에서 두 모임이 연달아 끝나면 두 번째 요청이 억제된다 — 현재 쿼터로는 드묾).
- `forClubId` 반응성(셋업 때 한 번만 읽음)·배열 쿼리 파싱·요약 카드 버튼 `disabled` — 진입점이 늘어나면.
- 모드를 빠져나가도 `?forClub=`·`?review=` 쿼리가 URL에 남아 새로고침하면 되돌아온다 — `router.replace({ query })`.
- 후기 딥링크의 `name`이 검증 없이 `place_reviews.place_name`에 저장됨 — 사내 앱이라 보류, 서버에서 같은 `kakaoId`의 기존 이름을 우선 쓰는 완화 가능.
- 상세 화면의 `placeLocked` computed는 시계가 흐르지 않음(탭을 열어둔 채 자정을 넘기면 버튼이 남음 → 서버 400).
- `upcomingPlaces`의 `meet_at` 경계 시각 테스트, 'inviting·canceled·done' 테스트 범위.
- `server/utils/clubView.ts`의 `export type { GroupedClubs }` 재수출은 이제 아무도 안 쓴다 — 빌드 WARN "Duplicated imports"의 출처. 두 줄 삭제(`clubSlots.ts`의 `kstParts` 재수출도 같은 모양).
- 저장소에 `vue-tsc` typecheck 스크립트가 없다 — 서버↔화면 타입 드리프트를 잡을 그물. 다음 정리 세션 후보.
- 2단계에서 이월한 `.ics` 줄 접기(RFC 5545 §3.1)는 여전히 미구현.
