## 무엇이 생겼나

에이전트가 **같은 책을 완독한 사람을 스스로 찾아** 모임을 제안하고, 관리자가 승인하면 초대가 나가고, 초대받은 사람이 수락/거절하는 데까지 동작한다.

- **순수 함수 3종** — `clubMatch`(점수식: 별점 분산 0.25·동시성 0.25·리뷰 밀도 0.2·부서 다양성 0.15·미참여 0.15), `clubSelection`(정원 초과 시 부서 다양성 우선 5명, 호스트 지정, 쿼터), `clubView`(목록 4묶음). 전부 DB를 모른다 — 그래서 테스트가 빠르고 mock이 없다.
- **`clubRepo`** — 후보 발굴(`findCandidateReaders`: 60일 내 완독·게스트 제외·3명 이상), 쿼터 상태(`quotaState`), 제안 저장(트랜잭션).
- **`clubService`** — 상태 전이. 승인 → 초대 알림 / 응답 → 3명 수락 시 scheduling, 남은 인원 3명 미만이면 즉시 취소 / 기한 만료 처리 / 마감 하루 전 리마인드(중복 방지).
- **`clubAgenda`** — 참가자들이 **실제로 쓴 리뷰**를 넣고 토론 질문 3~5개 + 근거(누구의 리뷰에서 나왔는지)를 만든다. 리뷰 없거나 실패하면 일반 질문으로 폴백. AI 설정 키 `club_agenda`가 관리자 화면에 자동으로 한 줄 늘었다.
- **`clubMatcher`** — 위를 조립. 회당 2건, 한 사람은 한 실행에서 한 모임만(`usedUserIds`).
- **범용 `notifications` 테이블 + 헤더 벨** — 책모임 전용이 아니다. 연체·예약 알림에 그대로 쓴다.
- **화면** — `/clubs`(초대/응답필요/참여중/지난), `/clubs/[id]`(참가자·아젠다·근거 인용·응답 버튼), 관리자 승인 큐("왜 이 조합인지" + 아젠다 초안 + 매처 수동 실행).
- **주기 실행** — `server/tasks/club/matcher.ts`(월 09:00 KST), `club/deadlines.ts`(매일 09:00 KST).
- **nav** — "리뷰" 자리에 "모임". 리뷰 페이지는 그대로 두고 내 서재에 진입점을 뒀다(321줄짜리 페이지를 540줄짜리 `my.vue`로 합치지 않기로 함).

## 어떻게 진행했나

subagent-driven-development — 태스크마다 새 구현자 + 리뷰어, 마지막에 브랜치 전체 리뷰. 14개 태스크 중 7개가 첫 리뷰에서 수정 라운드를 한 번 거쳤고, 전부 한 라운드로 끝났다. 잡힌 것들:

| 태스크 | 리뷰가 잡은 것 |
|---|---|
| T2 | `describeMatch` 문구 임계값(0.2/0.5)이 `CLUB_RULES` 밖에 하드코딩 — 계획 원문 결함 |
| T6 | `club_canceled` 알림 호출이 두 곳에 4/5 인자 동일하게 중복 → `cancelForLackOfMembers` 헬퍼 |
| T7 | `generateAgenda`의 try가 설정 조회·클라이언트 생성을 안 감싸 "예외를 던지지 않는다"가 미보장 |
| T8 | 정렬 테스트가 bookId tie-break만으로 통과했고 `expect(plain).toBeGreaterThan(0)`는 아무것도 검증 안 함; 같은 실행 내 중복 배제가 미검증 |
| T11 | `[id].vue`에 `watch:[clubId]` 누락(모임 간 이동 시 이전 데이터 잔류), 403/404가 빈 화면 |
| T12 | 벨의 `.badge`·`.panel`이 `main.css` 전역 클래스와 충돌 — 예전 `.wrap` 버그와 같은 원인 |
| T13 | **구현자가 계획 결함 발견**: Nitro는 태스크 이름을 `meta.name`이 아니라 파일 경로로 정한다. 평평한 `club-matcher.ts`는 `club-matcher`로 등록돼 cron 키 `club:matcher`와 영원히 안 맞았을 것 → `club/` 하위로 이동 |

최종 브랜치 리뷰(Important 6건)에서 잡은 것 중 중요한 둘:

- **호스트가 먼저 거절하면 거절자가 호스트인 채 scheduling에 들어갔다.** 거절 시점엔 수락자가 없어 재지정을 건너뛰고, 나중에 수락이 들어와도 다시 확인할 지점이 없었다. 실증됐고, 2단계의 host-only 장소 확정이 여기 얹히므로 반드시 고쳐야 했다. → `ensureAcceptedHost`를 scheduling 전이 직전 두 곳에서 호출.
- **초대 마감이 cron 경계와 같은 순간이었다.** 마감 = 매처 실행(월 00:00 UTC) + 72h = 목 00:00 UTC, 기한 작업도 매일 00:00 UTC. "내일 마감" 리마인드가 스케줄러 지터에 따라 50/50로 갈렸다. → 마감을 그날의 23:59:59 UTC로 정규화.

## 운영 노트 (배포 전에 알아야 할 것)

- **첫 부팅**에 `ai_settings`에 `club_agenda` 한 행이 `INSERT OR IGNORE`로 추가된다. 기존 행은 건드리지 않는다. 테이블 4종은 전부 `CREATE TABLE IF NOT EXISTS`.
- **`/_nitro/tasks`는 운영에 노출되지 않는다** — dev 프리셋에만 등록된다. 원격 트리거는 `POST /api/admin/clubs/run-matcher`(관리자만)뿐.
- **cron은 프로세스 로컬 시간.** Dockerfile이 `TZ`를 안 정하니 UTC이고, 그래야 `0 0 * * *`가 09:00 KST다. Railway에 `TZ=Asia/Seoul`을 넣으면 두 작업이 00:00 KST로 조용히 옮겨간다.
- **재시작은 놓친 실행을 따라잡지 않는다.** 월요일 00:00 UTC를 가로지르는 재시작이면 그 주 매처가 건너뛰어진다. 복구는 관리자 화면의 "매처 지금 실행". (같은 이유로 중복 실행은 구조적으로 불가 — 스펙 §11의 "마지막 실행 시각 기록"은 그래서 구현하지 않았다.)
- **아젠다 생성이 실패하면**(키 폐기 등) 일반 질문으로 제안이 나가고 `ai_usage`에 **0토큰 행**이 남는다. 관리자 사용량 화면에서 `club_agenda` 0토큰 행이 보이면 그 신호다.
- 로컬 dev DB에는 검증 중 만든 『함께 자라기』 모임 1건(inviting, 김민우·이서연·박지훈·한상우)이 남아 있다.

## 2단계로 넘기는 것

- `tests/clubService.test.ts`의 "기한 만료로 scheduling에 들어갈 때도…" 테스트는 이름과 달리 `respond`의 자기 승격 경로를 검증한다(3명째 수락 시 `respond`가 즉시 scheduling으로 넘기므로 `expireInvites`의 그 분기는 현재 도달 불가). 2단계 첫 태스크가 같은 두 지점을 손대니 그때 정리.
- 사람 쿨다운을 "종료 후 4주"로 재려면 `clubs.done_at`이 필요하다(지금은 `created_at` 기준, `done`이 2단계에서만 생겨 무해).
- `ensureAcceptedHost`가 "수락자 중 첫 사람"을 고른다 — 스펙의 "같은 기준(리뷰·참여 이력)"으로.
- `[id]` 핸들러 5곳의 id 파싱 2줄 중복 → 2단계에서 `votes`·`place`·`ics` 핸들러가 늘기 전에 `requireIdParam(event)` 헬퍼로.
- "리뷰가 없어 일반 질문입니다" 문구가 LLM 실패 폴백과 구분되지 않는다.
- scheduling 상태에서 아직 응답 안 한 사람이 "내 응답이 필요해요"에 들어가지만 할 수 있는 응답이 없다.
- 벨을 열면 20건 밖의 안 읽은 것까지 전부 읽음 처리된다.
